# Dispatch binding history and adoption

Ordinary `dispatch bind` cannot adopt history. With 945 open/UNKNOWN identities and 55 finite elapsed windows, a legacy root already holds 1,000 bindings. Adding one produces 1,001 retained bindings. Vanilla 0.7.48 cannot represent that state: its strict root schema rejects `dispatchHistory`, and lossless materialization exceeds its 1,000-row bound. Outbox or named-usage rollback does not qualify configuration rollback. An unqualified bind refuses before any history directory, image, profile rename or durable generation publication and reports the retained count, legacy limit and required reader. Legacy binds that fit 1,000 remain in the legacy JSON representation, including finite windows and exact idempotent replacements.

`withDispatchHistoryAdoption(supply, action)` is the explicit source integration interface. It has no CLI flag, environment default, permissive config receipt or Boolean verifier. The supplier must return a strict `dispatch-history-source-adoption/v1` contract for the exact source-profile SHA256, complete next-profile bytes, image SHA256/generation, terminal evidence digest and all root metadata/binding digests/counts. The UTC qualification window is half-open and at most 60 seconds. The contract must declare `sourceQualificationOnly: true` and `rolloutAuthorized: false`; it is technical evidence, not release-owner approval. Root owns the authenticated adapter and L2 alone authorizes adoption, installation and rollback.

The compatible rollback target is the **read-only PR453 history-aware reader** from exact commit `e7e937faa4960fa0a8cb5d5263361fc02894b7f6`, collector package version 0.7.48. It is carried as `scripts/fixtures/dispatch-history-rollback-reader-e7e937fa.cjs`, SHA256 `bc08c2edf8ae459a9085851b3131e655865ed11dfa6a103e82286653c49703f4`, protocol `plimsoll.dispatch-history-rollback-reader/v1`. This target is distinct from vanilla 0.7.48. Its source/input manifest and reproducible entry are in the source-review packet. The bundle uses actual strict profile/history schemas and attribution functions; SQLite remains an external frozen dependency. Qualification and operational retention require the matching frozen lock, Node ABI and better-sqlite3 dependency. A full previous collector runtime is not qualified by this reader fixture.

Before publication, the guard reads a private, owner-controlled, single-link, no-follow copy of that exact artifact and executes the pinned bytes in a fresh local reader process with an allowlisted environment. The reader reopens private copies of the actual planned complete profile and immutable SQLite image. Every root custody, hot/historical binding digest, generation and terminal marker must agree. Unknown, missing, stale, partial, wrong-root, wrong-reader, clock-invalid or tampered contracts refuse; a receipt alone cannot pass. The source profile is checked again after qualification and immediately before rename. A detected competing source change is preserved and requires reread. All profile writers, including internal publication helpers, use the gate. A profile cannot remove an archived root and leave its evidence ignored.

Integration has these separate obligations:

- Obtain written L2 adoption approval and independent Root source review. The source contract does not provide that approval.
- Hold older readers before migration. Preserve the exact current profile, all referenced immutable images, reader artifact, source manifest and frozen dependencies. There is no automatic generation cleanup.
- Select the retained history-aware artifact as the rollback reader, with **all writers held during rollback**. It supports bounded read-only inventory and exact current/delayed attribution; it does not authorize a full vanilla collector rollback or running mixed writers.
- Reopen the exact adopted immutable profile/image pair through that reader. Restoring an older profile or ignoring history would drop the new binding and is prohibited. Root/L2 must qualify the actual installed/released consumer pair separately.
- Use `rollbackCollectorDispatchHistory()` only when every binding fits the legacy cap and no terminal marker is lost. It still refuses the 1,001-binding state without writes.

An example of the source adapter boundary is `withDispatchHistoryAdoption(request => ({ contract: exactSourceBoundContract, readerArtifactPath: privateRetainedReader, dependencyDirectory: qualifiedCollectorPackage, scratchDirectory: privateOwnedScratch }), () => bindDispatch(args, now))`. Contracts must be rebuilt for each exact planned mutation; unrelated or stale certificates cannot authorize a new profile/generation. `closeDispatch(args, now, authority)` separately requires its original authenticated terminal proof. A completed turn, age, inactivity, null lifetime or failed attribution bind never proves native termination. The CLI close operation continues to refuse without that adapter; no placement retry is implied by any bind refusal.

The hot limit remains 1,000 per root and 64 roots. History remains bounded to 4,096 rows per root, 65,536 total rows, 16 MiB raw evidence, 32 MiB images, eight retained files and 256 MiB directory storage. Profile reads remain bounded to 32 MiB, query results to 1,024 rows/4 MiB and caches to two immutable generations. All existing duplicate/collision, custody, generation, continuation, restamp/incarnation and crash checks remain. Historical bindings are serialized once per update into membership sets and reused for record construction; the previous quadratic retention scan is removed. No TTL, cap increase, pruning, uncertain hand-close or collector version bump is introduced.

Qualification adds finite bounds: 64 KiB contracts, 2 MiB reader artifacts, 96 MiB encoded input and 64 KiB output. The reader process has a two-second deadline and SIGKILL on timeout, inside the unchanged five-second writer budget. A late caller callback or synchronous filesystem call is rejected after it returns; a callback/syscall that never returns still needs an external watchdog. The mutation-lock database still opens by pathname after pinned no-follow ownership/inode checks; hostile same-user replacement and power-loss durability remain unqualified boundaries. Cooperating writers use the existing BEGIN IMMEDIATE lock; same-user noncooperating races between the final check and rename require the owner-controlled-directory/held-writer contract.

Images are durable before atomic profile rename, which is the sole generation publication point. A lock COMMIT cannot undo that rename. Failures afterward require reread, never a blind older-profile restore. Old generations and partial/orphan images count against storage pressure and are not authority until selected by a complete profile.
