# Ledger copy retention proposal — eco-6hoxj.165.258

The snapshot removal command can be released independently. Ledger retention in this change is a design and a synthetic prototype, disabled by default and outside the production collector. It supplies no native ledger delete or compact command. Raw collector rows remain immutable: the proposed operation deletes only eligible local copies, never updates their values. Cloud retention and dispute retention remain separate obligations.

The source baseline is collector main `71d6ff27f0d39aa31d188c9bcc31d37bf188c384`, version 0.7.51. No cloud repository or production database was inspected or changed.

The ledger is more than raw events. `buffer.ts` creates `buffered_events` with its event JSON, privacy suppression metadata and receipt time, and `metric_samples`. Other collector modules add upload queue envelopes and terminal receipts, capture cursors and epoch state, source sightings, live producer keys, immutable usage identities, session and dashboard projections, finance coverage/rollups, context and enrichment repair queues, learning facts, account labels and dispatch attribution. The lane's `SOURCE-TABLES.tsv` inventories declarations from the collector source; it reports code inventory, not Studio0's actual schema or table sizes.

`upload.ts` keeps accepted local raw copies; `outbox.ts` writes terminal acknowledgment lineage and removes an acknowledged outbox item. Normal upload validates the per-item cloud acknowledgment against request and audience digests (`delivery-ack.ts`), then matches its lease and raw incarnation. The receipt table holds raw rowid, raw ID, created time and privacy generation, status and reason. It does not retain a per-row payload digest or a cryptographically verifiable archive of every acknowledgment. `upload-history.ts` opens the ledger read-only and does not mark ordinary delivery receipts; a successful history run alone is insufficient retention evidence.

The existing retention default is 90 days (`config.ts`). `AutomaticRetentionCadence` runs bounded slices, ordinarily 128 candidate rows, with a six-hour idle interval and five-second continuation; it defers to foreground maintenance. `LocalEventBuffer.prune` writes copy-expiry receipts and finance coverage watermarks. Its upload hold rules preserve current eligible unsent/dead remote deliveries. Those rules also allow expiry of certain offline, inactive-audience, locally ineligible or legacy uploaded-at-only rows without a verified per-item cloud receipt. Do not adopt those exceptions for this storage policy. This lane does not alter that existing policy.

SQLite deletion normally makes pages reusable while the file keeps its high-water size. The metadata evidence shows the live database plus WAL grew 111,149,056 bytes over 3,603.401592 seconds: 2.665059 GB/day. The broader Plimsoll directory grew about 2.7045 GB/day over another observation window. Continuing capture, delivery envelopes, indexes and derived state explain potential growth from source; which tables caused Studio0's growth, cloud backlog, retention progress, free pages and the age distribution are UNKNOWN. Source alone cannot attribute 2.665 GB/day to raw payloads or prove that retention is malfunctioning. [SQLite's page reuse behavior](https://www.sqlite.org/lang_vacuum.html).

The proposed native policy has these defaults, subject to release-owner acceptance: disabled; a 30-day minimum local window measured from both local capture and verified acknowledgment; a 100 GB soft budget for the entire main file plus WAL; 128 rows/50 ms per online writer slice; a 5-second continuation only after progress; and a once-daily byte/age preview. A 30-day stream at the observed rate is about 79.95 GB before retained-state overhead. The byte budget schedules more eligible work and reports pressure; it never shortens the window or releases an unverified copy. If holds and required state exceed the budget, the native result must report `capExceeded`, held bytes and coverage. A guaranteed hard bound during prolonged cloud outage is incompatible with retaining all unacknowledged data; capacity or an explicitly approved intake policy would be required.

Every candidate must pass all of these gates in the same writer transaction:

1. Its immutable identity includes the ledger/installation epoch, tenant/device audience, raw ID, raw created time and privacy generation. Rowid is a local reference and must also remain consistent.
2. The production delivery path has a valid per-item authenticated acknowledgment, or a newly verified retrievable cloud archive receipt. Legacy `uploaded_at`, an HTTP 2xx, an aggregate batch count, a history watermark, a local dead receipt or a changed audience never substitutes for that proof.
3. The receipt must match the immutable copy's identity, audience and payload digest. Persist a side-table verification certificate; never add or repair fields on the raw row. A legacy copy without this certificate remains held until the existing cloud receipt can be verified or the unchanged copy is safely re-acknowledged.
4. Both capture time and receipt time are older than the retention cutoff. Invalid/future clocks, unresolved lineage, active/dead-replay deliveries, unfinished projection repair, local replay, disputes and an active rollback dependency hold the copy.
5. Before DELETE, create a payload-free local-copy-expiry receipt with identity, digest, remote receipt reference, cutoff and policy revision. Preserve anti-reimport/deduplication and generation fences. Keep existing finance coverage watermarks and immutable usage pinning; compare every supported historical reader.

Required retained state after a verified cloud receipt:

| Consumer | Keep locally | Local raw copy after both windows |
| --- | --- | --- |
| Intake and deduplication | Epoch, capture cursors, source sightings/fingerprints, raw incarnation tombstones and usage pins | May expire only after all dependencies are settled |
| Upload and retries | Active/replayable dead queue items, lease/lineage state, verified acknowledgment certificates and terminal receipts | Any pending or replay hold prevents expiry |
| Local replay and export | Expiry coverage and a retrievable, independently verified cloud/archive path; retained raw within window | Expired local detail must say unavailable locally and link to verified history; never fabricate full local history |
| Finance, learning, session and dashboard readers | Immutable aggregates/usage pins, dimensions, coverage watermarks, repair queues and lineage required by those readers | A pending rebuild or uncovered historical query holds the raw copy |
| Disputes and evidence | Explicit dispute pins and accessible verified cloud evidence with its retention contract | Remains held until the dispute closes; cloud durability/retrievability must be demonstrated |
| Rollback | Lifecycle snapshots, runtime digests, ledger format/version floor, compaction journal, pre-swap generation and continuity manifests | A rollback-required journal forbids retention; expired-copy replay must remain compatible with the supported previous runtime |

All these dependencies require integration proof before enabling a production policy. The current cloud's receipt validation is verified in collector source, but an end-to-end retrievable history/archive contract was not tested in this lane. No cloud change is shipped.

The first native stage should reuse SQLite pages after bounded, verified copy expiry. This preserves implicit rowids, needs no second 118 GB copy and can stop much of future raw/index file allocation when free pages cover incoming writes. It does not promise immediate filesystem space reclamation. A bounded read-only metadata preview must report page size/count, freelist, main/WAL sizes, eligible/held bytes by age and cause, and complete/partial coverage. It must neither read payloads into operator output nor connect to the live HTTP service.

A one-time shrink needs an offline lifecycle operation with a mutation lease, proven ledger quiescence and a generation fence. APFS-clone the original to one owned rollback path when supported, or use the supported SQLite backup with measured headroom. Stage all copy expiry in a candidate; compare it with the unchanged source. `VACUUM INTO` may change implicit rowids, and `buffered_events` has a TEXT primary key while `upload_outbox`, receipts and repair cursors reference rowids. Therefore an unchecked vacuum-and-swap is unsafe. Either build a compact SQLite candidate with explicit rowid-preserving inserts and preserve every table/index/trigger, or reject a vacuum candidate whose complete surviving rowid/key manifest differs. Do not rewrite raw values or waive a mismatched reference. [SQLite's VACUUM and rowid contract](https://www.sqlite.org/lang_vacuum.html).

Before publication, require full integrity and foreign-key checks, identical retained-row identity/digest manifests, consistent outbox/receipt lineage, identical epoch/capture cursors/source sightings, identical usage and historical aggregate controls, honest expiry coverage, no dangling repair cursor, successful pending-delivery replay, a verified remote detail retrieval and no double-count on recapture. A sample is insufficient for a swap. Recheck quiescence, source inode/size/generation and lease immediately before rename. Fsync the candidate and a journal containing source/candidate hashes, verified expiry manifest and rollback path; close SQLite and refuse unknown WAL/SHM ownership. Atomically rename the staged file over the live path on the same volume and fsync its parent. Record recovery phases so a crash before the swap preserves the old file and a crash after it can either verify the published generation or restore the owned rollback copy. Reopen only through the normal collector generation admission path. Older runtimes must refuse the new recovery journal rather than delete the only way back. Collector startup/restart and operational receipt handling belong to a later release lane.

Keep one rollback clone until release-owner acceptance and a proven healthy collector generation, then remove it with a separately supported, manifested operation. Keeping a full independent rollback copy defers physical savings; an APFS clone can also retain shared extents. Never claim physical reclaimed bytes while the rollback copy still owns them. Disk notification below 20 GB remains a notice; unavailable copy headroom should choose page reuse/defer compaction rather than an unsafe swap.

The prototype is limited to metadata planning and a private synthetic SQLite fixture. It is off unless explicitly enabled in that fixture. It tests exact receipt/incarnation/content/audience matching, age, missing receipts, delivery/dispute/replay holds, unknown/partial totals, byte pressure, bounded continuation, immutable raw edits, payload-free expiry receipts, cursor and aggregate continuity, candidate identity checks, replay-held data, a known independent fixture copy, file-size shrink and rollback. Its successful vacuum fixture uses an explicit INTEGER PRIMARY KEY, unlike production's raw table. A negative identity test rejects a renumbered raw row. These tests demonstrate the design's controls; they do not prove a production migration, cloud archive retrieval, full historical readers, concurrency-safe publication or compatibility with 0.7.39/0.7.47 ledgers.

At the existing 90-day default, a steady stream at the observed rate would retain about 239.855 GB before other state. Do not promise that reducing the configured days or running a manual vacuum is safe. The release owner first ships the independently tested snapshot command; then accepts a production receipt-verification, page-reuse and publication implementation with the integration proofs above.
