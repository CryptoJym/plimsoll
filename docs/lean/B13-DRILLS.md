# B13 maintenance rebuild drills

This contract follows `BEADS.md` B13, `MIGRATION.md` §4 and `PROOF.md` §5 item 2b and §6. A copy drill uses `cp -cR` on the whole kept directory, verifies the cloned `work-ledger.sqlite` hash, and runs only on that clone. The `--copy-drill --copy-root` route never grants a live migration stage. A live invocation requires the `lean_rebuild_stage` receipt in `maintenance_state` with value `S10` or `ABORT`; the B2a migration owner must write that receipt when its stage gate is met. Until then the live preflight refuses with `stage_not_ready`.

## Writer pause and recovery boundary

The daemon and its maintenance and enrichment children own the target ledger connections. `LocalEventBuffer` takes an open token before SQLite opens and records its actual process-owned connection lease in `maintenance_state`; separate write-capable CLI, lifecycle and account-salt connections use the same opener, while the checkpoint worker's parent reserves a token until the worker exits. The 31-module statement inventory is a coverage list, not 31 observed connections. The rebuild receipt records token owners, SQLite PIDs and connection leases before and after unload, and again after taking the rebuild fence. A stale token fails closed and needs an operator to verify that its PID is gone before removing it. The rebuild first checks the stage, integrity, outbox count and headroom, using the greater of the operator WAL receipt, the last 24 hours of recorded WAL samples, and the current WAL file. It refuses a live run without a recent WAL sample. A headroom refusal is stored beside the ledger and surfaced as `maintenance.rebuild` in daemon `/status`; the receipt names reclaimable, required and shortfall bytes. The rebuild starts a ledger-free pause listener, unloads the daemon through the existing lifecycle authority, waits for the listener to bind, and refuses if any lease, token or file handle remains. The listener authenticates hook and OTLP pushes and answers `503` with `Retry-After: 1` without accepting or server-spooling them; the client owns the retry spool. `/status` declares `maintenance_rebuild` and a null claim `through`. The exclusive source connection stays open through verification and both renames, so a raw SQLite opener at the verify-to-rename boundary is blocked too. Once the file is swapped, the durable state becomes `resume_started` before the listener is released and the daemon is loaded. The fence stays held through daemon resume. The daemon must first own its versioned collector start lock and atomically claim one nonce-bound resume permit; only that process may reopen the rebuilt ledger until the fence is removed after load returns. A second `start` has no process-local claim and remains fenced. That boundary makes the old file forensic evidence: `--rename-back` and `--recover` refuse with `forward_repair_only`.

On an interrupted `VACUUM INTO`, `--recover` checks the untouched source, discards the incomplete target, and resumes capture. A kill between the two renames leaves the main basename absent; both CLI recovery and rename-back validate the canonical parent and state/backup paths, then restore it. A lock without a first state write can also be recovered after checking that the untouched source is intact. A failed target verification discards the target. A failed reopen after swap renames the old file back before the writer gate opens. The five dashboard snapshots are regenerated from the rebuilt projection rows at their original publication times and compared with the source publication; only the two work counters advanced after publication are excluded. Finance publication controls, schema hash, user version and every retained table count must also match before the swap; the reopened file runs `integrity_check` again. The Studio0 incremental backup alternative is a separate mode to select only if the rehearsal measures a plain rebuild pause above 15 minutes: copy pages while capture continues, then run a final catch-up and the same verify/swap/rollback boundary under the full pause. It requires a separate correctness drill for pages changed during the concurrent copy.

If lock creation loses a race after quiesce, the rebuild reloads its daemon without deleting the other owner's lock. Authenticated OTLP and live-usage maintenance 503s first write private, body-keyed refusal receipts; no server spool or ledger cursor advances. The resumed daemon retires one receipt only after the matching payload commits or reaches a durable intake spool. An absent retry leaves the capture claim unattested across restarts.

For a refused hook, the private receipt names a digest of the privacy-blanked caller body before the normalizer clamps its time or repository maintenance enriches the ledger row. A retry must resend that same body; JSON key order and valid UUID spelling may differ, but any other retained value change is a different event. Admission probes the digest-named receipt directly and writes the original-body digest to an immutable ledger column in the same transaction as the event and acknowledgement. Reconciliation uses the acknowledgement first, then only post-refusal rows with the same canonical ID, source, kind, session and immutable digest. A digest mismatch does not settle the refusal. An exact terminal rejection can still retire the receipt. Receipt retirement deletes its acknowledgement after the receipt unlink is durable; bounded retention also reaps an orphan acknowledgement once its event and receipt have gone.

An older 0.7.44 binary cannot write the immutable digest. Its consumed retry can be retired as `retired_unverified` only when the receipt names a client spool file that has gone, a row above the refusal high-water mark has the same canonical identity and no digest, and no such post-refusal row carries a digest. This is neither an acknowledgement nor a loss. The terminal journal records the metadata-only outcome before the receipt unlink, and its count appears in `/status` and the capture claim across restarts. The pending hold ends and attestation can resume with that visible count. A pre-refusal row, a still-present spool file, or an unavailable high-water mark cannot take this outcome. A missing retry after ten minutes with no candidate row remains the separate durable `hook retry lost` gap.

## Pending: abort after a copy-ready S2/S3 (PROOF.md §6 item 7)

**Blocker: B2a.** No copy can pass through its lean dual writer and converter yet. The current ledger has no B2a tables, conversion checkpoint or raw-admission census, so an arbitrary table drop and vacuum would not prove the abort bound.

When B2a is available, clone the Studio5 ledger, record pre-S2 live bytes and measured bytes per raw row, run its dual writer and converter through copy-ready S2/S3, and retain the B1 count of raw rows admitted since S2. Set `lean.write=off`, prove no new lean writes, drop only B2a's new tables, and run `maintenance rebuild --stage ABORT` under the full pause. Assert the rebuilt file is at most pre-S2 live bytes plus admitted raw rows times measured bytes per row; record peak bytes including WAL and compare the peak with the runway's reserved rebuild headroom. Assert outbox pending and all retained rows survive, the dropped tables are absent, spools drain, and `/status` returns to S0 with the abort reason. Failure of any comparison leaves the copy and the receipt for diagnosis; it never changes a host.
