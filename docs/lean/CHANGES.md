## 5. Assumptions B0 made on the lead's behalf (decide ambiguous points, report them)

- **The whole-ledger merge (a), not the refusal (b).** The brief offered an atomic whole-ledger merge or a refusal of a source ledger with more than one install plus a repair path. B0 chose the merge and holds it to be the smaller *correct* rule. (b) has no repair path for the case it refuses: the child V is not its own ledger, so it can never be linked separately, and the only exit would be the admin release, which loses the honest pre-re-join rows of exactly the Mac an admin is most likely to meet late (a lost key, an unlinked re-join, then a normal re-join with proof). (b) is not smaller in locking either: to refuse safely it needs the same lock-then-read-in-a-fresh-statement discipline and the same `FOR SHARE` on the join's previous install, since a join can add a member between the count and the update; it only replaces one multi-row `UPDATE` by a refusal. (a) is one rule, "the link moves a ledger, never an install", under which every round-11 check (S9, S10, S11, linked once) still holds with "install" read as "ledger".
- **The destination is refused, not resolved, when it is not a root.** The brief requires the destination to be the root of its own ledger; the refusal names that root so the admin can retry with it, which is the whole repair path. Resolving silently would hide a wrong target from the admin's receipt.
- **One audit row in a new table, and the per-install columns on every moved install.** The brief asks for one audit row; round 11 had no audit table for links, so `device_install_ledger_links` is new (tenant-scoped, in the erasure list, like the rebind's audit table), recording who, when, the source ledger, the destination and the counts, with its id on the admin's receipt. The reader asked for who and when *per moved install*: the merge stamps every moved install's `ledger_linked_at`/`ledger_linked_by` with the admin, overwriting a child's `join_proof` stamp, which named a ledger that no longer exists; the moved set is then the installs stamped with the row's `linked_by` and `linked_at`.
- **The join's lineage step holds the previous install's row `FOR SHARE`** (a one-line addition to C6) rather than a ledger-level advisory lock or `SERIALIZABLE`: it is the row lock every sighting already takes, the merge's `FOR UPDATE` on every member conflicts with it, and the merge's re-enumeration in a fresh statement is what makes the join's inserted member visible. Deadlocks between a merge and a sighting that names two installs in the opposite order are detected by PostgreSQL and retried like any other; C1 already allows `SERIALIZABLE` with retry as the alternative.
- **The response names the ledger.** Round 11 retried parked rows on `lineage: linked`, which a merged chain's member already had. Adding `ledgerInstallId` to the acknowledged response and retrying on a ledger change is the smallest rule that reaches every member; the collector records the ledger the refusing response named when it parks the rows, so a response for the same ledger changes nothing. C4 is not touched: `/status` keeps `lineage` and `parkedRows`.
- **The refusal is a 409 with the reason as its message**, like `StampFromOtherLedgerError` carries `stamp_from_other_ledger`, so the pending tests match on the reason and the receipt can quote it.
- **Should-fix: seed B rather than correct the comment.** The reader offered either; seeding B makes the pending test's history the reader's S8 history, and no other case depends on P's actor.
- Mem0 and the agent Inbox were not used from this seat (the packet was self-contained; the Inbox reported no pending message at start); the Studio4 census was not re-run.

##### 5. Assumptions B0 made on the lead's behalf (decide ambiguous points, report them)

- **Refuse and hold, not the weaker promise.** The read offered two ways out of blocking 1: require that the pair's install is in the uploader's ledger, or make an explicit weaker promise that cross-ledger attribution is accepted. B0 chose the requirement. It keeps the protection today's ingest already gives (a registered install's rows carry its server-bound actor; `ingest.ts:397-427`), it is one sentence to state and to test (guarantee 5, the S8 crossing enumeration), and it closes R7 by construction rather than by a per-ledger fact view. The weaker promise would have had to be signed as a new, weaker ownership contract.
- **Hold, rather than fail closed, on delivery through an unlinked ledger.** Answering null on delivery would still split from a member the old install's summary judged as the version's actor (an honest issued pre-re-join row: S9h). Holding gives one row one answer whatever the pair: the row is not judged until the ledger is linked, and then it is judged in the same ledger as the member. The admin link is the repair for an unlinked re-join, as the admin rebind is for a poisoned pair; an honest collector reaches the hold only with a lost or rotated key.
- **The admin link re-keys the linked ledger's facts and is allowed once.** Without the re-key, a pair poisoned in the unlinked ledger would be judged issued in the linked ledger (SQL S10 flips to E); with it the fact follows the install. A chain is linked once (a second link would need a second re-key and an audit of the first), so `linkLedgerByAdmin` refuses an install already in another ledger.
- **The fact keeps its ledger column** although, with the refusal in place, every judged pair satisfies `ledger(install) = ledger(U)` and the column is derivable for judgment. Keeping the round-10 key (which the read confirmed) avoids reopening the schema test and makes the re-key an explicit, auditable `UPDATE`; B6 may treat the column as the ledger's index of its facts rather than as a discriminator.
- **`actorForStamp` gains a required `ledgerInstallId` and throws** rather than returning a "held" answer. The one ownership function must refuse on both paths, and a returned "held" could be exported by mistake; a thrown refusal cannot. The pure test's helper defaults the reading ledger to the binding's own ledger for the round 8-10 cases (all same-ledger); the five predicate calls of the Postgres test pass X's ledger.
- **Two nullable columns on `device_installs`** (`ledger_linked_at`, `ledger_linked_by`) record how and when an install joined a ledger other than its own, rather than a new audit table: the link is a rare, one-time event per install and the certify needs only who and when.

#### Round 8, §5: Assumptions B0 made on the lead's behalf (decide ambiguous points, report them)

- **The stamp is the pair `(install, version)`, not a bare version.** The reviewer's repair scoped the *stored* version to the install; without the install on the identity row and on the wire, the predicate's `install` argument is undefined for a row delivered after a re-join (a row still in the outbox would be judged against the new install and unallocated although its version was issued by the old one). One nullable column (`summary_members.actor_binding_install`), one allowlisted metadata key and a pair-keyed parts map close that gap; the alternative, resolving the install from the row's installation epoch on the cloud, is fragile because the epoch id is collector-generated and learned only from claims.
- **The not-issued fact is sticky per `(install, version)`, so a faulty stamp poisons its version for that install** (rows the install later stamps legitimately with it are unallocated until an admin rebind issues a fresh version). A per-row verdict cannot make two rows with the same pair agree, and the cloud cannot tell a faulty stamp from a stamp issued later except by the order of sightings; the poisoning is disclosed on the certify with the affected row count. Honest collectors never produce a not-issued pair (C4 clears the pair at a re-join).
- **`G_owed` keeps the reviewer's form `max(0, G_gate − C_conv)`** rather than a remainder proportional to converted rows: ~~the converter's byte counter self-corrects to real widths~~ (**corrected in round 9**, review-r2 should-fix 5: it does not; the rule is exact at 1.25 × and safe only up to it), the proportional form would need per-class row accounting, and the fixture shows the retained margin is exactly the 1.25 allowance (the whole allowance on the census-era G until completion). #### Round 6, in plain words (moved here from SUMMARY-FOR-JAMES.md)

- **A summary of each day can now be acknowledged by the cloud.** Deleting a raw row requires the cloud to have acknowledged every summary that used it, and one of those (the per-day summary) had no way to be sent or acknowledged, so in practice nothing would ever have been deleted. - **Who owns activity captured while a Mac was offline is now the same answer whether or not it reached the cloud.** If an admin re-binds a Mac from person A to person B while it is offline, last round's rules could export the same activity as A's if it never uploaded and as B's if it did. Now both paths use the same stamp the collector wrote at capture, the cloud records when the Mac acknowledged the change, and the answer no longer depends on delivery. Test: `b4_offline_rebind` (seven orderings, the reviewer's included).
- **Every timestamp the collector accepts now reaches the day totals.** The collector accepts some unusual but valid timestamp formats; last round's plan would have dropped those records from the dashboard's day sums as "contract violations". - **The disk-runway check before a Mac's no-delete hold used a stale growth figure.** The temporary tables the migration adds are about **59% of the raw table on Studio1, not 42%**, once the per-row identity and link rows are counted.
