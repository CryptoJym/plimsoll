### 2.2 The member ledger, the seal, and the deletion proof (the only path that deletes a raw row)

**Targets and segments.** Every aggregate that is folded from raw rows is a *target* row in `summary_segments` (§3.3): a **session** segment, an hourly **rollup** bucket segment, or a **day** target (one per epoch, source and UTC day, the parent of the three day-fact tables, §3.5). A target is identified by `(target_kind, base_key, segment_seq)` and referenced by `target_ref`, an `integer primary key autoincrement` that SQLite never hands out twice, even after the highest row is deleted (`out/fixtures/b3_durable_target_refs.py`).

**Covering targets (B1).** Every raw row has **exactly two** covering targets, and its membership is one identity row in `summary_members` plus one `summary_member_edges` row per covering target (`out/fixtures/b1_membership_edges.py`):

| Row class (`summary_members.row_class`) | Base target | Second target |
|---|---|---|
| `usage_session` (satisfies `<UR>`, has a session id) | its session segment | its day target |
| `usage_sessionless` (satisfies `<UR>`, no session id) | its hourly rollup bucket segment (counted, never its amounts) | its day target |
| `activity_session` | its session segment | its day target |
| `activity_sessionless` | its hourly rollup bucket segment | its day target |

Turn summaries are derived at fold time from the session's members and are never recomputed from raw rows after the session segment seals, so they are not a covering target (§3.2). The S2 and S3 certifies check the edge set of every raw row against this table (MIGRATION.md S2 (b), S3 (a)). The **base key is epoch-scoped**: it always contains `epoch_key = coalesce(installation_epoch_id, '')` and `source`, so an identical session id in a second installation epoch is a different base key, as it is on the cloud (§5.2; the reviewer's epoch counterexample, replayed in `out/checks/counterexamples.log`, case 7).

**Lifecycle of a target.**

1. `open`: raw rows fold in, in rowid order; each fold writes the row's identity row in `summary_members` (at its first fold) and one `summary_member_edges` row `(event_id, raw_generation, target_ref)` per covering target, in the same transaction, and advances `high_water`. **No member of an open target can be deleted** (step 1 of the proof below refuses). A dirty open target (a raw update or delete of a member, or an insert below `high_water`) is recomputed from all its live members, which all exist, so the recompute is exact.
2. `sealed`: the target is sealed when its seal rule fires (session segment: disposition terminal and 30 minutes quiet, or the segment is 7 days old and 5 minutes quiet; hourly bucket: bucket end plus 2 h; day segment: day end plus 48 h; every kind: the target is not dirty). Sealing is one transaction: an **exhaustive recompute from every live member** (all present) must equal the folded counters, `member_count` and the additive `member_sum_digest` are frozen, `sealed_revision`, `sealed_at_ms` and `residue_sum_digest = member_sum_digest` are set, and the segment is uploaded as a revision with `sealed = true`. A sealed target is **never recomputed from members again** (principle 7).
3. After sealing, a raw insert whose target would be this sealed target (a late row, a reused rowid below `high_water`, or a re-admitted id that passes the rule below) is folded into the next **open segment** `(base_key, segment_seq + 1)`; the sealed segment is untouched. A raw update or delete of a **surviving** member of a sealed target is not folded: the trigger writes `sealed_member_mutations (target_ref, event_id, kind ∈ {update, delete, generation_rewrite}, at_ms)` and bumps the target's `post_seal_mutations`; readers show that count, and a segment with `post_seal_mutations > 0` is listed in `/status` and in the S4 certify report. A `generation_rewrite` also updates the membership row's `raw_generation` so identity follows the raw row.
4. `retired`: every member is a tombstone and the last-chunk audit has passed; the row itself is deleted only by the retirement proof below, never by age (B3).

**Digests.** `H(id)` is the first 16 bytes of `sha256(lower(trim(id)))` read as a 128-bit integer; `member_sum_digest = Σ H(id) mod 2^128` over all members, stored as 32 hex characters. It is order-independent and **subtractable**, so the cloud can compute it from its own raw ids alone and both sides can maintain a residue after deletions (`out/checks/counterexamples.log`, case 17; §5.3).

**Durable identity.** Every check below matches on `event_id = r.id` and `raw_generation = g`, never on rowid. `raw_rowid` on facts and membership rows is a live pointer (nullable, unique only while non-null); the deleting transaction sets it to null. A rowid reused later by SQLite meets no constraint (case 1).

**The deletion proof for an activity row `r` = `(id, g, rowid)`**, run by the lean retention job (B10b) inside one SQLite transaction per chunk (≤ 5,000 rows, never sampled), only after the hold in §2.4 has been lifted on that host (MIGRATION.md S9):

1. **Every covering target sealed and acknowledged.** The identity row for `(r.id, g)` is `live`; its edge set is exactly the required set for its row class (the table above); and for **every** edge target `T`: `T.state = 'sealed'`, `T.acked_revision ≥ T.sealed_revision`, `T.acked_member_sum_digest = T.member_sum_digest`. One open or unacknowledged target among them refuses the row and names the target (`out/fixtures/b1_membership_edges.py`: a sealed session with an open day target refuses); a `dead`, `conflict` or `stale` receipt refuses. The day target's acknowledgement arrives only through the `day_summary` receipt of §5.2 (round 6); under the round-5 item table no receipt could reach it, so no row of any day was ever deletable (`out/fixtures/b1_day_target_receipt.py`).
2. **Per-row membership.** The identity row's `raw_rowid` equals `r.rowid`, each edge's `folded_revision ≤` its target's `sealed_revision`, and the identity row's `payload_digest16` equals the digest of the raw row's stored payload now. Every row of the chunk is checked individually; none is inferred from a sample.
3. **Counters and residue, per covering target.** For each covering target `T`, before the delete: `T.live_member_count = T.member_count − T.tombstone_count` and `T.residue_sum_digest = member_sum_digest − Σ H(tombstoned ids)` (maintained transactionally; both are recomputed exhaustively in step 4). After the delete: `tombstone_count += n`, `live_member_count −= n`, `residue_sum_digest −= Σ H(chunk ids)`.
4. **Exhaustive audit at the boundaries.** The counters were recomputed exhaustively at the seal, while every member existed (lifecycle step 2); after the seal no counter is ever recomputed. Before the **first** proof chunk of a target the job runs the **identity audit** over every membership row of the target: `Σ H(live member ids) + Σ H(tombstoned ids) = member_sum_digest`, `live_member_count + tombstone_count = member_count`, and `residue_sum_digest = member_sum_digest − Σ H(tombstoned ids)`; when `tombstone_count = 0` it also recomputes every counter from the live members and compares them with the sealed values (a free extra check, impossible once the hold-release ladder of §2.4 has tombstoned a member of the target, which is why it is not the rule). After the **last** chunk (`live_member_count = 0`) it recomputes `Σ H` over the tombstones and asserts it equals `member_sum_digest` and that the residue is zero. A mismatch marks the target `integrity = 'audit_failed'`, deletes nothing, and lists it in `/status`. Chunks between the boundaries rely on the seal, steps 2-3 and the receipt; nothing is ever recomputed from a partial member set (`out/checks/counterexamples.log`, case 2).
5. **R elapsed** since the seal's acknowledgement; `r` is not in the never-delete set (§2.3); the session's cloud coverage relation is not `partial` or `unknown` (§5.3); `T.post_seal_mutations = 0` for this chunk's target (a mutated segment is deletable only after the mutation record is acknowledged as part of the next revision).
6. **Tombstone and receipt.** The identity row becomes a tombstone (`raw_rowid = null`, `deleted_at_ms`, `state = 'tombstone'`); its edges stay until each target's last-chunk audit ("Retirement" below); a `raw_retention_receipts` row is written with reason `lean_proved_activity`; the raw row is deleted. The second chunk of the same target passes because steps 1-3 read the seal and the tombstones, not the surviving members (`out/checks/counterexamples.log`, case 2).

**For a usage row** (satisfies `<UR>`):

1. A `usage_facts_local` row exists with `event_id = r.id` and `raw_generation = g`.
2. The fact's `upload_state = 'acked'`, its `delivery_id` has an `upload_receipts` row with `terminal_state = 'acknowledged'` (`collector-cli/src/outbox.ts:701-709`), and `envelope_digest` on the fact equals the digest of the `base_envelope_json` stored for that delivery when it was enqueued (`:678-699`). A dead receipt never counts.
3. The `capture_root_observations` receipt for `r.id` exists where the source is a tailed root (`collector-cli/src/capture-root-inventory.ts:206-258`); push sources have no root and skip this check.
4. The usage row's two covering targets, its session segment (or its hourly rollup bucket when it has no session id) and its day target (§3.3, §3.5), are **sealed and acknowledged** (steps 1-3 above apply to it as a member; `out/fixtures/b1_membership_edges.py` runs the sessionless case).
5. R elapsed since the acknowledgement; not in the never-delete set. Receipt reason `lean_proved_usage`; the membership row becomes a tombstone.

**Re-admission of a deleted event id.** After a raw row is deleted its id can be inserted again: tailed sources are refused by the root receipt (`capture-root-inventory.ts:229-241`); push sources (hooks, OTLP, live usage) are not. The admission hook therefore looks the id up in `usage_facts_local` and in `summary_members` (tombstones included) **before** writing anything:

- **live membership row or live fact**: today's `insert or ignore` is a no-op, as now (`collector-cli/src/buffer.ts:2342-2352`);
- **tombstone or acknowledged fact with the same payload digest**: the row is **refused** as a duplicate (the hook or OTLP client receives the same success it receives for a duplicate today), `readmissions` on the tombstone or fact is incremented, and nothing else is written. No new raw row, no new member, no new upload;
- **different digest**: the raw row is admitted with `privacy_disposition = 'quarantined_readmission'`, an `activity_readmission_conflicts` or `usage_fact_conflicts` row is written, the row is **withheld** from upload, is in the never-delete set, and is listed in `/status`. This is the local twin of the cloud's `conflict_stored_fact_differs` (`cloud src/lib/ingest.ts:511-518`).

The reviewer's re-admission counterexample (a deleted id re-admitted with no retained membership) is replayed in `out/checks/counterexamples.log`, case 3: the tombstone makes the decision.

**Tombstones (bytes recalculated, should-fix 2).** A tombstone is the identity row `(event_id, raw_generation, row_class, payload_digest16, actor_binding_version, deleted_at_ms, readmissions)` with its primary-key index and the partial live-rowid index: about **125 B** (estimate from column widths, BUDGETS.md §3), plus its two edges (about 92 B each) until the covering targets' last-chunk audits drop them, so about **310 B** while edges exist. Every raw row, usage or activity, has an identity row, so tombstones scale with **all** raw rows: Studio1's whole history (276,454 raw rows, `out/checks/plan-arithmetic.log`) is about 35 MB of post-audit tombstones (5.5% of raw bytes) and about 85 MB while edges exist (13.7%); per 1,000 usage rows that is 0.19 MiB at Studio1's 0.61 activity rows per usage row and 0.69 MiB at the production hour's 4.8. The accumulation is indefinite until B14 proves a dedupe horizon, so its **rate** is a Studio0 gate (BUDGETS.md §3, §6). B1 measures each host's ratio and the density gate in BUDGETS.md §2 includes it. Tombstones are compacted only by B14 with a proved dedupe horizon, exactly like `capture_root_observations`.

**Retirement of a segment row (B3).** A `summary_segments` row is never deleted by age. When a target's **last** proof chunk has passed its final audit (`live_member_count = 0`, `Σ H(tombstones) = member_sum_digest`, residue zero), the job deletes that target's tombstone **edges** in the same transaction; the tombstone identity rows stay. A segment row is then deleted only by the **retirement proof**, run with `PRAGMA foreign_keys = ON` on the lean writer's connection (no `foreign_keys` pragma exists anywhere in `collector-cli/src` at `92c33bf`: grep this round; B2a sets it) and asserting before the delete that the target has zero rows in `summary_member_edges`, zero in `sealed_member_mutations` and zero children in the three day-fact tables, and that its base row (session or rollup) is past its own retention. A referenced segment therefore cannot be retired, and because `target_ref` is `autoincrement` a retired number is never issued again (`out/fixtures/b3_durable_target_refs.py`: the round-4 rule aliases an old tombstone to a new segment after rowid reuse; the round-5 rule refuses the retirement and the next number is fresh). Day targets consequently live with their day facts (1,825 days); session and rollup targets retire shortly after their last chunk and their base row's retention.

**Every raw delete, by any path, tombstones.** The raw-delete trigger converts the identity row of `old.id` into a tombstone (`raw_rowid = null`, `deleted_at_ms`, `state = 'tombstone'`) whether the delete came from the proof, from the hold-release ladder (§2.4, receipt reason `lean_hold_release_acked`) or from a local erasure, nulls `conversion_rejects.raw_rowid` for `old.id` (round 8, `CONTRACTS.md` C3), and, through `summary_member_edges`, updates **every** covering target's `tombstone_count`, `live_member_count` and `residue_sum_digest` in the same trigger (`out/fixtures/b1_membership_edges.py`: the day target's counters see all four deletions). For a sealed target it writes `sealed_member_mutations (kind = 'delete')` only for a delete that is neither the proof's nor the ladder's (an erasure), so a disclosed deletion is not double-counted as a mutation. The ladder never deletes a member of an open or dirty target (§2.3), so an open target's recompute always sees every member; the pre-S2 ladder (no membership exists yet) leaves receipts only, and S3 converts the affected sessions as `cloud_superset` (MIGRATION.md §3, §6).

**Receipt reasons.** `raw_retention_receipts.reason` has `check (reason = 'retention_window_elapsed')` (`collector-cli/src/buffer.ts:331-338`), and SQLite cannot alter a CHECK. The B10b release rebuilds the table in one transaction (`create table raw_retention_receipts_v2 … check (reason in ('retention_window_elapsed','lean_proved_activity','lean_proved_usage','lean_hold_release_acked'))`; `insert … select` from the old table; drop; rename), then reopens the ledger so `dashboard-projection.ts` recreates its raw-delete trigger, which reads the table by reason (`:1160-1167,1254-1267`). The retained-live path is re-sourced from `usage_facts_local` in B4 before B10b deletes any usage row, so the trigger's `'retention_window_elapsed'` test never sees a lean receipt for a live-usage row before the new path exists. `out/checks/counterexamples.log`, case 11, replays the rebuild in SQLite and shows the old and new reasons both accepted afterwards.

**Replacing today's guard.** Today `prune` treats a row as unprotected when `uploaded_at` is set **or** an `upload_outbox` row exists (`collector-cli/src/buffer.ts:3008-3013`), and deletes at `retentionDays` age (`:2997-3004,3041-3052`; scheduled with `maxRows: 128`, `collector-cli/src/cli.ts:3074-3083`). The lean retention job replaces that predicate with the proof above; `retentionDays` becomes the ceiling for local facts, not a raw-row deletion rule. Between the hold (§2.4) and S9 the prune deletes nothing at all, except under the disclosed hold-release ladder in §2.4.

### 2.3 Never deleted by any job or any budget step

Unacknowledged usage rows and their facts; raw rows whose delivery is pending or dead; rows in `usage_fact_conflicts` or `activity_readmission_conflicts`; `capture_root_observations`; tombstones (until B14); dead receipts; `capture_gaps`; pending or conflicted repo-context links; the current and the last acknowledged revision of every segment; any member of an open or dirty target; any raw row of a session whose cloud coverage relation is `PARTIAL` or `UNKNOWN` (§5.3); any raw row whose sealed segment has unacknowledged post-seal mutations; `conversion_rejects` (every row, resolved ones included) and any raw row with an open `conversion_rejects` row (round 8, `CONTRACTS.md` C3).

### 2.4 The temporary no-delete hold: code now, deployment per host with a measured runway (blocker 5; B10a)

Two layers, both **built and tested on a ledger copy now** (B10a) and **deployed on a host only at that host's S1b** (MIGRATION.md S1b), never earlier:

1. **Configuration, reversible, no code.** `retentionDays` accepts up to 3,650 (`collector-cli/src/config.ts:67`). Setting it to 3,650 on the host puts the prune cutoff about ten years in the past (`buffer.ts:3004`), so the bounded prune pass selects no candidates and deletes no raw row and no metric sample; the finance retention watermark is untouched because it advances only for deleted rows (`collector-cli/src/history-coverage.ts:275-280`). `/status` already reports the policy and cutoff (`buffer.ts:3108-3123`).
2. **Code, in the same collector release that ships the writer (B2a).** A `raw_retention_control.hold_reason` column (`raw_retention_control` exists, `buffer.ts:339-349`); while it is non-null, `prune` returns without selecting candidates and `/status` shows `retention.hold = "lean_migration"`; the lean retention job (B10b) is the only code path that clears it, and only after S9's first proved chunk. Red/green test: with the hold set, a raw row with a pending outbox entry, a dead receipt, no marker at all, or an acknowledged receipt is never deleted at any age; with the hold cleared and the old predicate, the pending-outbox row is deleted (today's defect reproduced, PROOF.md §5 item 1).

**Why the hold is not switched on early.** A hold stops today's deletions for the whole migration (S1b to S9: an estimated three to six weeks per host, MIGRATION.md §2), while capture keeps appending raw rows and the catch-up (B21) adds the unread files' rows. Round 3 gated this on a one-time free-space formula that contains no capture-growth term; a light Mac could fill between checks with no safe deletion path (review R11). Round 4 therefore requires, before the hold is set on a host:

- **measured full-hold growth**: at least seven days of B1 samples on that host of **gross ledger growth per day**: the daily increase of `(page_count − freelist_count) × page_size` plus the bytes of the raw rows today's prune deleted that day (its receipts, `buffer.ts:3035-3039`, times the host's measured bytes per raw row, 2,262 B on Studio1, `out/checks/plan-arithmetic.log`); under the hold nothing is deleted, so gross growth **is** the hold's growth. The WAL 24 h high-water is sampled separately. The catch-up must be complete before the seven-day window closes so its rows are inside the samples. From these B1 computes `hold_growth_per_day = p95_7d(gross growth) × (1 + g_host × raw_share)`, where `raw_share` is the raw table's share of the ledger (0.47-0.58 on the four measured light hosts, `out/checks/plan-arithmetic.log`) and `g_host = G_gate / raw bytes` is the **same** conservative figure the numerator subtracts (round 7, `CONTRACTS.md` C2; round 6 used the unfactored estimate here; `fixtures/s1b_runway_host_bound.py`) until S2 measures it on that host;
- **a runway**: `runway_days = (free_disk − reserve − G − rebuild_headroom) / hold_growth_per_day` with `reserve = max(5% of the volume, 2 × WAL_24h, 2 GiB)` (hypothesis, calibrated by B1), `G = G_remaining` (round 7, `CONTRACTS.md` C2): `G_gate = 1.25 × G_host` where `G_host` is computed from the host's **own counted cardinalities** (usage rows, raw rows, sessions, session-day rows, day rows, rollup buckets and day targets, each counted by B1's read-only census on a `VACUUM INTO` copy of a light host's ledger, taken after the catch-up, at most a day before the S1b decision and re-taken before S3, the copy made only with free space ≥ ledger + reserve, with the segment proxy counted; the copy's measured peak on busy hosts and Studio0), never from another host's mix scaled by ledger size; the 1.25 covers the row-width estimates until S2 has measured them on a copy; a host without a fresh counted census has no gate value; while conversion runs `G = G_owed = max(0, G_gate − C_conv) + g_gate × U` (round 8, `CONTRACTS.md` C2: `C_conv` the converter's own written bytes, never the lean tables' page count, which holds the live writer's rows too; `U` the raw bytes admitted since the census that no lean row covers yet; `g_gate = G_gate / raw bytes at the census`), 0 once everything is folded, so dual-write bytes are never counted as conversion progress and post-census rows are still owed; and `rebuild_headroom = live bytes × 1.2`; the hold may start only when `runway_days ≥ max(30, 1.5 × planned hold days)` (`out/checks/counterexamples.log`, case 15: a host that passes round 3's one-time gate and fails the runway at a plausible growth);
- **a continuous alarm** while the hold is on: B1 recomputes `runway_days` every 60 s from the current free space, `G_owed` and the trailing 7-day p95 growth, publishes it with `runway.g = {gate, owed, converterWritten, unfoldedRawBytes, leanTableBytes, basis}` in `/status` and the collector log (`leanTableBytes` is disclosure only), and the lead's daily check reads it;
- **an abort ladder that preserves capture evidence**, run by the collector and disclosed in `/status`: at `runway_days < 10` the converter pauses (it is the largest consumer, BUDGETS.md §4.2); at `< 5` the hold is **partially released**: the prune resumes under a stricter predicate than today's, deleting only raw rows older than `retentionDays` (the original 90 days) **whose delivery is acknowledged**: `uploaded_at is not null` **and** an `upload_receipts` row with `delivery_id = e.id` and `terminal_state = 'acknowledged'` exists (a raw row's delivery id is its own event id, `collector-cli/src/outbox.ts:662-671,701-709`); never a pending, dead, unmarked or withheld row, never a usage row whose fact is unacknowledged, never a member of an open or dirty target (`out/checks/counterexamples.log`, case 12); with receipt reason `lean_hold_release_acked` and a tombstone where membership exists (§2.2); the S3 certify then treats those sessions as `cloud_superset` (the cloud holds their acknowledged rows) and converts them from cloud-origin rows (MIGRATION.md §6); at `< 2` the host **aborts the migration**: `lean.write = off`, the new tables are dropped, the rebuild runs (MIGRATION.md §4 step 8), and the host returns to S0 with the reason recorded. Nothing unacknowledged is deleted at any rung.

The S1b gate is: the code hold verified on the host, the configuration set, the runway computed from measured growth and above its floor, all observed in `/status` and in the preflight receipt, before S2 starts. Layer 1 alone protects hosts still on 0.7.40; layer 2 makes the protection independent of configuration drift. Neither layer changes what the tailers capture or what uploads do.

## 3. What is summarized at capture, and the exact schemas

All new tables live in the same SQLite ledger (one writer, WAL as today). Time columns are Unix milliseconds unless named `*_at` text (ISO, as today's tables). Every segment carries a `*_version`, a monotone `revision`, a `digest`, and missingness counters so a reader can tell "zero" from "not captured". Digests over members are the additive `member_sum_digest` of §2.2 on both sides.

**M6 rule `m6_v3`.** Spend after failure is accumulated **per tool class and per model**: from a failed attempt of class C, every following turn's known cost is added to C's bucket **and** to the (C, turn's `model_key`) bucket, up to and including the next turn with a successful result of C (or the session end); a turn following failures of two classes is counted in both (the page says so). Turns whose cost is unknown are counted in `cost_unknown_turns`, never as zero. The class×model table is what M6's "by tool class, source and model" aggregation reads (DECISION-METRICS.md M6); two allocations of the same class total across two models now produce different stored fields (`out/checks/counterexamples.log`, case 8).

**M8 rule `m8_v2`** is unchanged: for thresholds 100k, 150k and 200k tokens, turns whose `context_tokens` exceeds the threshold contribute `(turns, cost_nanos)` to the total and to the turn's `model_key` bucket; a mixed-model turn is attributed to its dominant model and counted once. ### 3.5 Day-grain dashboard facts, the UTC day key, the exact boundary, and the versioned window contract (B2, B5; round-3 blocker 3)

**Why day grain, and why a new contract version.** The five snapshots are cut at `now − days × 86,400,000 ms` (`collector-cli/src/dashboard-projection.ts:545-547`); the window builders decide membership per event by comparing the **`observed_at` strings** (`fact.observedAt >= window.cutoffAt`, `:2185-2196`); the daily series and the compact buckets use `day(value) = value.slice(0, 10)` (`:549-551`; `:1917,1961,2010,2258`); a session's per-window totals are recomputed from its facts when the cutoff passes through it (`:2411-2420`). No aggregate coarser than the event can reproduce a millisecond cutoff, and per-event timestamps for 1,825 days are the copy this program removes. So the contract changes, explicitly and versioned: **`DASHBOARD_SCHEMA_VERSION` 3 cuts every window at a UTC day boundary**, `since = UTC midnight of (now − days)`, and every group the snapshot shows is rebuilt from day-grain rows.

**The day key is the UTC day of the parsed instant.** The shared schema accepts any timezone offset (`collector-cli/packages/shared/src/schemas.ts:65-73`) and the buffer stores the text unchanged (`collector-cli/src/buffer.ts:2360`); the projection already parses it to `observed_at_ms` (`dashboard-projection.ts:598,797`). Round 4 defines `day = strftime('%Y-%m-%d', observed_at_ms / 1000.0, 'unixepoch')`, computed in code from `observed_at_ms`, on every new table (`observed_day` on facts, `day` on the day tables). For `2026-09-25T23:30:00-02:00` the slice gives 2026-09-25 and the UTC day is 2026-09-26, and a string compare puts that row before the next UTC midnight although its instant is after it (`out/checks/counterexamples.log`, case 6). Which producers can store a non-Z offset at the pin: hook bodies that carry their own time are kept untouched (`collector-cli/src/server.ts:345-364`), transcript records pass `observedAt` through (`collector-cli/src/transcript-tailer.ts:269-275`), rollout records are clamped but not normalised (`collector-cli/src/rollout-tailer.ts:1690-1691`); OTLP normalises to `Z` (`collector-cli/src/otlp.ts:106-122`).

**The boundary, exactly (B5).** Today's rule includes a fact in a window iff `fact.observedAt >= window.cutoffAt` as **strings** (`collector-cli/src/dashboard-projection.ts:2189`, re-read this round), and the cutoff is `new Date(now − days × DAY_MS).toISOString()` (`:545-547`), so at a frozen UTC-midnight instant every cutoff string is `YYYY-MM-DDT00:00:00.000Z`. The round-5 rule includes a fact iff `observed_at_ms >= cutoff_ms`, where `observed_at_ms = Date.parse(observed_at)` (the collector's existing parser, `dashboard-projection.ts:500-504`). **For a midnight cutoff C the two rules differ for a row s iff `(s >= C_str) != (Date.parse(s) >= C_ms)`.** Which strings can reach that state is fixed by the schema: `observed_at` is any string `Date.parse` accepts that ends in `Z` or `±HH:MM` (`collector-cli/packages/shared/src/schemas.ts:64-73`, re-read this round), and `Date.parse` (node v20.20.2, `out/checks/node-date-parse.log`) truncates fractions beyond three digits, accepts a missing seconds field, a space or lowercase `t` separator, a date with a bare `Z`, `T24:00:00` as the next midnight, and RFC-2822-style strings such as `Sat, 26 Sep 2026 00:00:00 GMT+00:00`, while refusing lowercase `z`, `+0000` and bare dates. Over a **finite corpus** of 3,812 schema-valid strings drawn from that grammar (`out/fixtures/b5_lexical_boundary.py`), every string that differs at some midnight cutoff falls in one of three **census classes**, each computable per row without knowing the cutoff; the corpus proves those cases, not the unbounded `Date.parse` grammar, and the census is **conservative** by construction (below):

| Census class | Predicate on the stored string `s` | What lands in it |
|---|---|---|
| `day_move` | `substr(s,1,10) <> UTC day of Date.parse(s)` | any non-zero offset whose local date differs from its UTC date (the round-4 case `2026-09-25T23:30:00-02:00`); `T24:00:00` |
| `before_own_midnight` | `s < substr(s,1,10) || 'T00:00:00.000Z'` | an explicit offset, zero or not, at local `00:00:00` (the reviewer's `2026-09-26T00:00:00+00:00`, `-00:00`, `-02:00`, the no-seconds `T00:00+00:00`); a fraction of four or more digits beginning `000` at `00:00:00` (`.0009Z`, `.000500Z`); a space separator at **any** time of the day (`2026-09-26 12:00:00Z`) |
| `non_iso` | `s` does not begin `YYYY-MM-DD` | the RFC-2822-style and month-name strings the schema admits; lexically a string that starts with a letter or with `2026/` sorts after every ISO cutoff (the old rule includes it in every window) and one that starts with a lower digit (`1 Sep 2026 …`) sorts before (excluded from every window); its instant is known (`out/checks/node-date-parse-r6.log`) |

The byte-parity set is the **canonical shape** `YYYY-MM-DDTHH:MM:SS.sssZ`: a canonical string and a midnight cutoff string are same-format fixed-width strings whose lexical order is their chronological order, so `(s >= C_str) = (Date.parse(s) >= C_ms)` at every cutoff (a property of the format, not of the corpus; the SQL census labels exactly that shape `canonical`). Every other row is examined **in code, per cutoff**, whatever class it lands in, so a grammar string outside the corpus cannot pass as parity unexamined. Within the corpus no string outside the three classes differs at any cutoff, and the classes are a superset (conservative): `2026-09-26T00:00:00+02:00` is a `day_move` row that agrees at every cutoff. So the **census** (MIGRATION.md S0, B9a) counts rows by class per host, and the **harness** (PROOF.md §4) evaluates the census rows exactly, per cutoff, with the rule above; the census SQL (in the fixture) marks every row that SQLite's own date parser cannot read, such as `T24:00:00` or a space separator, for the code pass instead of trusting SQLite's rounding.

**Exactly which of today's numbers change.** For a census row: (a) a `day_move` row's day in the `daily` series and in `dashboard_daily_window` moves to its UTC day, and so does its compact-segment bucket (`bucket_day`, `:835-846,864-871`) and the per-(day, source) compact totals; (b) any census row's membership in a window whose cutoff flips for it (computed per cutoff) enters or leaves that window; (c) a `non_iso` row is **kept**: it is folded into the day tables by the UTC day of its parsed instant (today's `day()` slice gives it a non-date bucket such as `Sat, 26 Se`, and today's string rule puts it in every window or in none by its leading characters), and its per-cutoff window membership is evaluated by the boundary rule like any other census row (`out/fixtures/b5_non_iso_day_facts.py`). **Every accepted timestamp has a day.** `contract_violation` is reserved for a stored string that `Date.parse` rejects (NaN), which the schema (`collector-cli/packages/shared/src/schemas.ts:65-73`) would have refused at intake; the converter records it as a counted `capture_gap` with reason `contract_violation` **and** keeps its event id in `conversion_rejects`, listed in `/status` and the S3 certify; nothing is dropped silently after acceptance (round 6). **`conversion_rejects` DDL (round 7, `CONTRACTS.md` C3):** keyed by `(event_id, raw_generation)` with the live `raw_rowid`, `epoch_key`, `source`, `reason ∈ {contract_violation, payload_unreadable, day_key_unresolvable}`, a value-blind `detail`, the sha256 of the stored `observed_at`, the `gap_id` of its counted gap, first/last seen and `attempts`, and `resolved_at_ms` when a later pass folds the row; never deleted by age or pressure (§2.3), compacted only by B14; its raw row stays in the never-delete set while the reject is open, and the raw-delete trigger (§2.2) sets its `raw_rowid` to null so a reused rowid never aliases it (round 8, `CONTRACTS.md` C3; collector `tests/contracts/lean/conversion-rejects.contract.ts`). Nothing else changes: totals, by-source, by-model, sessions, repos and accounts move only through (a)-(c). **Measured on this host:** the round-4 census (`out/checks/ledger-offset-census-r4.log`) classified suffixes only; the round-5 **shape census** on Studio3's live ledger, read-only on 2026-09-25 (`out/checks/ledger-shape-census.log`), found 202,074 rows, **all 24 characters in the canonical `T…sssZ` shape**, zero `day_move`, zero `before_own_midnight`, zero `non_iso`; the correction changes nothing on Studio3. The same census is the S0 baseline on every other host and its per-host class counts are the exact size of the change there.

**The parity promise, restated.** At a frozen instant T that is a UTC midnight, schema 3 equals schema 2 **byte-for-byte on every retained field for every canonical-shape row**; for every other row (the census rows; the SQL census sends every non-canonical row to the code pass) the two schemas differ exactly by (a)-(c) as the harness computes them per cutoff, and the harness must show that the difference equals those rows' moves and nothing else (PROOF.md §4). On a host whose census is zero, that is byte identity; on any other host it is identity plus an enumerated, versioned correction. Beyond raw retention the comparison is against the raw-row and compact-segment oracle only, as in round 3, because today's long windows hold token, cost, session, repo and account content for the trailing 90 days only (`:2047-2076`; `:607-614,1268-1286`).

### 5.3 Collector-origin versus cloud-origin: the exact coverage relation, and the residue deletion proof

A session can have a cloud-origin summary (from cloud raw rows, S4 backfill) and a collector-origin summary (from local rows, including rows whose delivery is dead or withheld). Neither is preferred by default. **The relation is a property of the base key** (a session, or a sessionless bucket), computed over **all** its segments, sealed and open; segments are the unit of assignment and deletion, not of the relation. On every held collector-origin revision, and again in the S4 certify, the cloud computes for the base key: `C` = all its own raw rows of that session or bucket (assigned or not), `cloud_count = |C|`, `cloud_sum_digest = Σ H(C)`; and compares with the item's session-level `memberSumDigest` (Σ over every segment of all local members) and `deliveredMemberSumDigest` (the same over local members whose delivery is acknowledged):

| Relation | Test | Reader uses | Cloud raw delete for the segment |
|---|---|---|---|
| `equal` | `cloud_sum_digest = memberSumDigest` and `cloud_count = memberCount` | collector-origin (the certify also asserts every member-derived counter equals the cloud-origin recompute; a mismatch with equal membership is a rule bug and fails closed as `origin_conflict`) | allowed after certify and seal |
| `collector_superset` | `cloud_sum_digest = deliveredMemberSumDigest` and `memberCount > deliveredMemberCount` | collector-origin; the page shows "N rows never reached the cloud" from `missing_delivery_rows` | allowed after certify and seal (the collector holds the extra rows in its never-delete set) |
| `cloud_superset` | `cloud_count > memberCount` and the collector's member ids are a subset of `C` (proved by the paged id exchange) | cloud-origin (the collector expired rows before the lean writer existed, or released them under the hold ladder) | allowed only after the cloud-origin summary is certified and sealed |
| `partial` | any other outcome of the id exchange | **neither**: the session is flagged `coverage_conflict`; counts are shown as "at least max(collector, cloud)"; no single figure is authoritative | **never** while `partial` |
| `unknown` | digests differ and the id exchange has not completed | as `partial` | never |

**Paged id exchange.** When the digests do not settle the relation, the cloud returns `coverage = unknown` and the collector answers with `membership_page` items (≤ 5,000 sorted event ids per item, resumable; the 1.88 M-row session on Studio0 (`HOSTS.md:19`) needs about 380 pages) until the cloud has the full set; the cloud then stores the relation with the ids it lacks and the ids the collector lacks. **Resolution paths** for `partial`: the collector replays its dead or withheld deliveries for the session (the rows still exist locally, §2.3), or an operator accepts the union after review; both re-run the relation. **Gates:** S5's cloud reader switch requires every session in the tenant to have a stored relation and at most 0.1% of sessions `partial` or `unknown`, each displayed flagged; the S4 certify report lists every `partial` session with both digests and counts; cloud deletion refuses any chunk containing a `partial` or `unknown` session. A reason-only mismatch report is not a gate; the stored relation is.

**Segment assignment (exact, by id).** Every cloud activity row carries a nullable `segment_ref`. It is set once, never by time: (1) when a sealed collector-origin segment arrives and the **unassigned** rows of its base key have `Σ H = ` the segment's `memberSumDigest` with the segment's `memberCount` (or its delivered digest and count), every one of them is assigned to the segment in one chunked update; (2) otherwise the paged id exchange for that segment (`membership_page` items, the segment's sorted ids) assigns exactly the rows whose ids the collector listed and records the **lacking-id list** (ids the collector holds that the cloud lacks) on the segment; rows of the base key that the collector did not list stay unassigned (they belong to a still-open segment, or are cloud-only rows that only a cloud-origin segment will own); (3) a row that arrives later for that base key (a dead delivery replayed) is assigned by lookup in the lacking-id lists of its sealed segments before it is treated as new, and removed from the list; a row in no list belongs to the open segment. For a **cloud-origin** segment (S4 backfill) the cloud's own `created_at` is the segment boundary, which is exact because it is the cloud's own column. A row is never in two segments, and a segment's member set on the cloud is `segment_ref = seg`, whatever the rows' `created_at` (`out/checks/counterexamples.log`, case 4: a session whose sealed segment has ten members the cloud lacks and one later row of the open segment relates as `collector_superset`; the ten arrive after a later row and are still assigned to segment 1, and the later row is untouched).

**Cloud residue deletion proof (blocker 1, R07).** Cloud activity rows of a sealed segment are deleted in chunks of ≤ 5,000 rows (MIGRATION.md §6). The stored segment carries `member_count`, `member_sum_digest`, `deleted_member_count` and `residue_sum_digest`. Each chunk's transaction: (1) relation ∈ {`equal`, `collector_superset`, `cloud_superset`} and the segment is sealed; (2) the chunk selects only rows with `segment_ref = seg`, walking `id`; rows of other segments or unassigned rows are never touched by this segment's deletion; (3) `count(rows with segment_ref = seg) = member_count − deleted_member_count − |lacking-id list|` **before** the delete (the decreasing residue), else refuse and mark `integrity = 'audit_failed'`; (4) delete the chunk, `deleted_member_count += n`, `residue_sum_digest −= Σ H(chunk ids)`; (5) at the **first** chunk, `Σ H(all rows with segment_ref = seg) + Σ H(lacking ids) = member_sum_digest` is recomputed once (O(N) once, not per chunk); at the **last** chunk `residue_sum_digest = Σ H(lacking ids)` and no assigned row remains; a lacking id that arrives afterwards is assigned and deleted by the same proof on its own, and the residue reaches zero only then. Chunk two passes because the invariant is the residue, not the original count (`out/checks/counterexamples.log`, case 4: 10,000 members in two chunks, ten late-delivered members deleted by a third chunk, and a later row left alone). Usage rows are never deleted by this program. After the tenant's first cloud deletion, the cloud sets `activity_lane_closed_at` for every install that passed S7, and the v1 event lane refuses activity rows from those installs with reason `activity_lane_closed` (§4); this is the second forward-repair boundary for the S7 flag (MIGRATION.md §8).

### 5.4 What summaries never do

Summaries never enter `reconcileUsage` and economics totals never read them, so no amount is double counted: usage records remain the only source of amounts. The cloud ingest budget stays: a batch is accepted whole or rejected whole.

### 5.5 Versioning

The cloud tables carry `contract_version = 2` and the collector's `/status` reports the negotiated version. A future change is a new payload kind (`activity_summary_v3`), never a silent change to v2 items.

## 6. Capture watermark v2, backpressure, gaps and tailer completeness

### 6.1 The claim

Today's claim is strict v1 with `gaps: [{from, to}]` capped at eight and replaced outright by the newest claim (`cloud src/lib/capture-watermark/contract.ts:68-105,193-201`; `collector-cli/src/outbox.ts:567-595`; `collector-cli/src/capture-frontier.ts:67`). Claim v2 keeps every v1 field and semantics and adds `declaredGaps: [{gapId, revision}]`, the ids of the gap items the collector has stored durably in `capture_gaps` (v2 items in §5.2), so the claim itself stays small while the gaps persist on the cloud by id, and `faults: [{faultId, kind, atMs}]` for unresolved durability faults (§6.3). The store rule for the **event** batch is unchanged: the claim advances only when every event in the batch is held (`cloud src/lib/capture-watermark/store.ts:24-58`). For a **summary** batch the claim advances only when every item's receipt is `held` or `duplicate`; a `conflict` or `stale` receipt leaves the watermark unchanged (mixed-item acknowledgement). A summary batch **with zero items** carries a claim alone (§5.1), so a withdrawing claim never waits for new events. PR #151 moved the seven-day active window into `active-window.ts` (`cloud src/lib/capture-watermark/active-window.ts:1-8`) without changing the claim schema.

### 6.2 Coverage

`captureCoverageForPeriod` (`cloud src/lib/capture-watermark/contract.ts:407-424`) keeps its rule and adds: `complete` is false while any persisted `capture_gaps` row for an active install overlaps the period, whatever the latest claim says, and while any unresolved fault is recorded for the install. A later claim cannot erase a persisted gap; only a gap item with a higher revision that closes or resolves it (for example after a successful replay or parse) can. An **open** gap (`ended_at_ms` null, §3.6) overlaps every period from its start onward, so no period after an unresolved file's last write is complete until the file is parsed (`out/fixtures/sf5_unresolved_file_open_gap.py`).

### 6.3 Failing closed, durably (blocker 4)

**Nothing is consumed without its gap row.** A tailer advances a file cursor, a spool drains a pushed file, and a refused row is counted, only in the **same SQLite transaction** that writes the corresponding `capture_gaps` row (or admits the row). If that transaction fails (SQLite error, disk full), nothing was consumed: the file's unread bytes stay unread and the existing uncovered-file machinery keeps reporting them (`collector-cli/src/capture-frontier.ts:24-32,294-304`); a pushed request is answered 503 with `Retry-After` so the client spools (hooks already spool locally, `collector-cli/src/server.ts:340-344`). No claim can call the interval complete because the frontier never passed it.

**The fault is persisted outside the ledger.** On any such failure the collector (1) sets an in-memory fault that forces `through = null`, `unattested = 'gap_record_unavailable'` on every claim until cleared; (2) writes a **marker file** `capture-fault.json` beside the ledger (a few hundred bytes: fault id, kind, at, source, file-key digest) and, when the ledger is writable again, a `capture_faults` row; (3) uploads the fault in the next claim's `faults` and, once the ledger accepts writes, a `capture_gap` item with reason `gap_record_unavailable`, `count_basis = 'unknown'`, `interval_basis = 'fault_interval'` over `[fault_at − write lag, resolved_at]`, which the cloud persists (§6.2) so that no later claim can stand as complete over it. The marker file's write can itself fail on a full disk; then the in-memory fault stands for the life of the process, and the restart rule below covers the crash.

**The restart rule.** At startup the collector **unlinks** a `capture-clean-shutdown` marker file (an unlink needs no free space) and reads `capture-fault.json`. At clean exit it recreates the marker **only if no unresolved fault exists**. If at startup the marker was absent (unclean exit, or an exit with an unresolved fault) or `capture-fault.json` exists, the first claim of the process is `through = null`, `unattested = 'restart_unverified'` and stays so until (a) every fault row is resolved (its gap row written and acknowledged) and (b) a complete whole-root coverage walk has finished after startup (`capture-frontier.ts:499-522`). So an older "complete" claim on the cloud is withdrawn by the first claim after the crash, and never by a claim that has not re-verified coverage. The residual window in which the cloud still shows the pre-crash `through` is from the fault to the first claim after restart; the cloud shows the claim's age, and the persisted `gap_record_unavailable` gap covers the interval retroactively once uploaded. PROOF.md §4 "Watermark v2" tests the crash and restart, and the old event inside a newly written file (§3.6).

**When storage is full.** A failed gap write with reason `storage_full` follows the same path; in addition the collector frees only space it owns and nothing in the never-delete set: `PRAGMA wal_checkpoint(TRUNCATE)`, then `error_samples`, then `metric_samples` older than 1 h, then retries the gap write; capture of activity stops (nothing is consumed), usage records continue into the reserved band as long as the reserve is physically present (BUDGETS.md §4.4), and `/status` shows `storage_full`. The reserve in BUDGETS.md §4.4 is what makes the gap row writable in the ordinary 100%-of-cap case; a full **volume** is the case this paragraph covers.

**Under post-migration budget pressure** (BUDGETS.md §4) the collector may refuse new activity rows; it records a counted gap per source with the interval, uploads it, and `/status` shows it. Usage records are protected: they are admitted into reserved headroom; if even that is exhausted the collector stops tailing and declares an unknown-count gap that also sets `dropped_usage_rows = null`, shown as a floor with unknown loss on totals.

### 6.4 Tailer completeness is part of the claim

A complete seven-day G1 with zero *declared* gaps proves nothing about files the tailers never finished reading. Today the automatic passes read only recent Codex day folders and files written in the last 48 hours (`capture-frontier.ts:13-17`), a partial retry can be dropped and pre-enrollment generations are excluded (`LANE-ROOT-CAUSE.md:3`), and the coverage walk is capped per turn (`CAPTURE_COVERAGE_MAX_WORK_PER_TURN = 4,096`, `CAPTURE_COVERAGE_MAX_ENTRIES = 200,000`, `capture-frontier.ts:63-65`) so a walk can stay incomplete; an incomplete walk changes nothing (`:512-517`). The read-only check found 7.9 GB unread on five hosts (`UNCOVERED-EVIDENCE.txt:16-47`; per host in `out/checks/plan-arithmetic.log`). Claim v2 and `/status` therefore carry, per source and per configured root:

- `bytesDeferred` and `deferredGenerations` from the last automatic pass (`collector-cli/src/rollout-tailer.ts:1263-1289`; the Claude and Grok tailers gain the same fields);
- `coverageWalk = {completedAt, complete, rootsConfigured, rootsCovered, entriesVisited}` from the last whole-root walk (`capture-frontier.ts:499-522`);
- `unreadFiles = {count, bytes}` grouped by the classes of `UNCOVERED-EVIDENCE.txt` (`no_tailer_row`, `work_remaining`, `behind`, `no_row_pre_epoch`, `unresolved:*`), each unread or unresolved file declared as a `capture_gap` with the matching reason and the interval basis of §3.6.

The rules: the frontier never advances past the oldest unread byte of a parseable file; an `unresolved:*` or never-read file is a declared unknown-count gap from the epoch start with **no end** until it is parsed (§3.6); a claim whose last whole-root walk is older than 24 h or incomplete attests `through = null` with `unattested = 'coverage_walk_incomplete'`. G1 shows all three fields (DECISION-METRICS.md G1) and MIGRATION.md gates S3, S6 and S7 on them.
